## Segment hypotheses, not demonstrated demand

Prioritize by whether a team can already name a blocked write, explain why its existing controls are insufficient, provide an authoritative effect lookup, and commit an engineer. These are hypotheses derived from the [wedge's three action criteria](/Users/sellers/Documents/GitHub/agent-middleware-api/WEDGE.md:22), not claims about segment sizes, willingness to pay, or incident prevalence.

| Hypothesized team and action | Proposed first buyer/operator to test | Why it could fit | Fastest disconfirmation |
|---|---|---|---|
| Internal AI platform team: synthetic refund or account-credit creation in staging | Platform owner plus application engineer; budget owner unknown | Duplicate value-changing writes may keep autonomy human-gated; the runbook already uses an illustrative refund | Existing idempotency and authoritative lookup already resolve timeout uncertainty and authority consumption at acceptable cost |
| Infrastructure automation team: staging resource allocation or quota change | Infrastructure/platform lead plus tool owner | Duplicate allocation or incorrect quota consumption could have an operational consequence | Actions are desired-state/idempotent, easy to undo, or require private connectivity unavailable in the supported pilot |
| Business operations automation team: synthetic order or fulfillment instruction | Automation lead plus system owner; commercial sponsor unknown | Reissuing an ambiguous instruction could create a second downstream job | Actual pain is bad model judgment or data quality rather than retry identity, dispatch, and uncertainty |

All three remain **not verified**. Exclude read-only copilots and harmless duplicate writes from the first wedge. Do not recruit regulated production workloads just because their consequences are severe: the current support boundary excludes their data. Test a staging analogue only if the partner can establish relevance without sensitive arguments. No evidence here supports choosing a named company or asserting an economic buyer's budget.

The strongest competing solution to test is the team's current stack plus upstream idempotency and effect lookup. The repo itself lists this as a disconfirming signal. Ask for a walkthrough of the last actual timeout, near miss, or blocked deployment before showing the demo. Evaluate the best baseline the partner can actually operate: existing gateway authorization and consumption limits, workflow retry controls, upstream idempotency, retained result/effect lookup, and current incident evidence together. Do not win a comparison by testing a deliberately naive “retry every timeout” baseline. If the combined current controls already resolve the restriction, the separate gateway needs another demonstrated reason to exist. This is an experimental requirement, not a claim that every vendor supplies all those controls. ## Three competing product, UX, and deployment theses

These alternatives are falsifiable interview concepts. Only A fits the currently supported product. B and C are not a feature backlog, supported deployment promise, or permission to implement anything.

| Thesis | Product and user experience | Deployment and buyer implication | Evidence that would support it | Disconfirmer / smallest test |
|---|---|---|---|---|
| **A — Keep one managed inline transaction boundary** | One engineer routes one staging tool; the primary artifact joins logical action, consumed authority, one gateway dispatch, uncertainty, and separate reconciliation. Existing docs/CLI are the pilot UX. | Existing dedicated vendor-managed Railway pilot. A platform owner accepts another dependency because it removes a specific autonomy restriction. | Partner accepts this exact boundary, passes the owned fault/replay/reconciliation test, identifies risk that returns if removed, and commits commercially. | Their existing controls are sufficient or latency/security/availability objections make this deployment unacceptable. Test with the existing qualification sheet and one-tool runbook. |
| **B — Put the primitive inside the partner's existing control point** | The buyer wants transaction semantics but will not add a separate managed gateway; it prefers an embedded adapter/library or ownership within its current gateway. | Unsupported concept; customer-operated/BYOC and new adapters remain frozen. A maintainer/operator, rather than a new SaaS buyer, may own the decision. | Repeated concrete objections to A while the same teams show an unresolved transaction problem and commit an owner/tool/date for an exact alternative. | “We prefer a library” without a committed implementation owner or buying path is preference, not demand. Conduct a paper architecture walkthrough; build nothing until a named-prospect exception is documented. |
| **C — Reconciliation practice is the useful service; the gateway is unnecessary** | The pain is resolving ambiguous effects, so a manual incident worksheet using the partner's existing idempotency, logs, and effect lookup supplies enough value. | No new runtime deployment for the experiment. It may reveal a consulting/documentation opportunity or no defensible standalone product. | The partner can safely remove the autonomy restriction through existing controls and a repeatable reconciliation process, without this gateway. | If authority consumption and dispatch races remain uncontrolled, a worksheet cannot claim A's guarantees. Compare one historical incident under current procedures against the proposed gateway record. |

Prefer A only provisionally because it is executable within the repository's scope, not because demand for it has been shown. If B wins discovery, record a **narrow/reframe** decision before engineering an alternate boundary. If C suffices, stop claiming that an inline product is necessary.
