140: ## What it guarantees
141:
142: | Guarantee | What it means | Proof |
143: |---|---|---|
144: | **Charge-once under retry** | Same idempotency key → same receipt, no second dispatch, no second debit. A changed payload under that key conflicts. | `tests/test_adversarial_five_claims.py` |
145: | **Budget containment** | A permit's `max_credits` is reserved by one atomic guarded `UPDATE`; concurrent invocations cannot over-spend it, including on SQLite. | `tests/test_permits.py`, `postgres_permit_concurrency` CI job |
146: | **Interrupted-call accounting** | For the configured upstream tool, one persisted chain links the idempotency record, reservation, debit, dispatch attempt, receipt, and audit event. Ambiguity after the send claim is receipted `delivery_uncertain`, never silently redispatched. Local governed tools have no dispatch state machine and fail closed into manual review. | [docs/failure-semantics.md](docs/failure-semantics.md) |
147: | **Offline-verifiable receipts** | Ed25519-signed; verifiable with no credentials and no network access to the issuer, using the SDK verifier or any JOSE tooling. | `GET /v1/receipts/{id}/portable`, `/.well-known/jwks.json` |
148: | **Authority before money** | Out-of-scope, expired, revoked, or tampered permits are denied with a reason code *before* any charge. When a valid permit was present, that refusal is itself a signed receipt. Unpermitted and unknown-tool calls fail closed without one. | `tests/test_adversarial_five_claims.py` |
149:
150: CI runs the full release gate as one required check (`trust_release_gate`), so
151: these claims cannot regress into `main` unproven.
152: [docs/PROOF_MATRIX.md](docs/PROOF_MATRIX.md) maps every proof command to the
153: invariant it asserts — and to what it does not prove.
154:
155: ## What it does not do
156:
157: - **Not universal exactly-once.** Gateway replay safety makes the *remote* side
158:   effect exactly once only if the upstream tool also honors the forwarded
159:   idempotency key.
160: - **Not proof of downstream effect.** The dispatch claim is committed *before*
161:   the network send, so it records the authority to send — not that a send
162:   happened, and never that the tool acted.
163: - **Not settlement or compliance.** An internal credit ledger, not merchant
164:   settlement, dispute handling, or a certified compliance record.
165: - **Not an IAM replacement.** Wallet isolation is application-layer
166:   authorization and query scoping; PostgreSQL RLS and a public multi-tenant
167:   isolation guarantee are not implemented.
168: - **Not a transparency log.** Receipts verify offline, but nothing is anchored
169:   externally, and audit chains are tamper-evident rather than immutable against
170:   an administrator who controls both the database and its chain metadata.

1: """What a contended receipt insert is allowed to tell the caller.
2:
3: The receipt is the last write on the governed money path, and it was the only
4: one without a write-conflict restart: the wallet debit, the permit reserve, the
5: idempotency record and the dispatch attempt all wrap theirs in
6: ``run_with_write_conflict_retry``. So once those stopped losing SQLite locks,
7: the surviving contention landed on ``INSERT INTO receipts`` and escaped as an
8: unclassified JSON-RPC ``internal_error``.
9:
10: That is the specific thing this file exists to prevent, and the reason it
11: matters is the one written on ``LedgerWriteContendedError``: a client that
12: cannot tell an unclassified failure from a named retryable one has to assume
13: its money may have moved. The case actually observed in CI was a *denial* --
14: ``outcome='denied'``, ``reason_code='permit_budget_exceeded'``,
15: ``credits_charged=0`` -- where nothing had been charged and the true answer was
16: sitting in the row that failed to insert.
17:
18: The classification splits the same way the audit chain's does, and for the same
19: reason (see ``tests/test_audit_chain_contention_surface.py``):
20:
21: - a refusal that ran nothing may say "retry", because a second attempt costs
22:   nothing and no terminal record was left behind;

24:   a second execution of something the caller has paid for.

FILE tests/test_audit_chain_contention_surface.py
1: """Where an audit-chain loss is retryable, and the one place it must not be.
2:
3: ``append_chained_audit_event`` retries a contended per-wallet chain head 64
4: times and then raises ``AuditChainContendedError``. What that should mean to
5: the caller depends entirely on whether the call had already run.
6:
7: A refusal that ran nothing -- a permit denial, a lost quote -- can say "retry":
8: no tool executed and no wallet moved, so a second attempt costs nothing and the
9: first left no terminal record behind. That is the retryable ``-32005`` answer.
10:
11: Every audit write past the charge is the opposite, and is the reason this file
12: exists. It audits *after* the tool ran and the wallet was charged, so "retry"
13: would invite a second execution of a call the caller already paid for. Nor can
14: it be softened into a success: ``create_receipt`` takes
15: ``audit_event_id=audit_event.event_id``, so no audit event means no signed
16: receipt either, and ``reconcile_stuck_records`` repairs a stuck record only when
17: a receipt exists -- without one it counts the record for manual review instead.
18: The honest answer there is its own non-retryable code, ``-32007``: the state is
19: one the pipeline classified deliberately, so spending the unclassified
20: ``-32603`` on it hid a known outcome among genuine bugs and left a client free
21: to read "internal error" as "try again".
22:
23: Finalization is only the most obvious of those sites. The local
24: refund-succeeded path and the upstream post-charge helpers audit after
25: execution too, and guarding finalize alone left both free to hand a caller who
26: had already run and paid a "retry" -- so each is pinned separately below rather
27: than trusted to a shared reading of the control flow.
28:
29: The retryable half carries its own obligation, tested here too: the -32005 has
30: to name a retry the caller can actually make. A governed call has an
31: idempotency record open by the time these refusals happen, and reconciliation
32: deliberately does not delete uncharged local records, so a record left in
33: progress would meet every retry of that key with ``idempotency_in_progress``
34: forever.
35:
36: The last two tests pin that obligation from both sides.
37:
38: A remote refusal has already driven its dispatch attempt terminal, and
39: ``mcp_dispatch_attempts`` pins the record by a NOT NULL foreign key, so the
40: release cannot happen at all -- the unwind's DELETE raises and is only logged.
41: There the retryable answer has to name the reconciler that owns the record
42: instead of a retry of the key.
43:
44: A local refusal behind a human-approval gate is the opposite, and is why the
45: retryable answer is kept there rather than withheld. The single-use approval is
46: spent, so the retry is refused -- but refused with a signed, receipted
47: human_approval_consumed denial, which is a terminal answer. Withholding the
48: release to spare the caller that refusal would strand the key instead, in
49: exactly the way the paragraph above describes, and no ``-32007`` would be owed
50: either: nothing was charged and nothing ran, so there is no committed effect for
51: that code to name. The second request is asserted, not just the first, because
52: that is where the difference shows.
53: """
