3: ## Project Mission
4:
5: This repo is being evaluated as possible trust infrastructure for autonomous agents.
6: Do not treat it as a generic agent app backend.
7:
8: The strongest thesis:
9:
10: > A control layer for agent-to-tool actions where every autonomous action is scoped, authorized, metered, signed, receipted, auditable, and governable.
11:
12: The weaker thesis to avoid:
13:
14: > An agent backend with lots of features.
15:
16: ## Core Loop
17:
18: Judge the product against this loop:
19:
20: discover → authenticate → authorize → invoke → meter → receipt → audit → govern
21:
22: Every major feature should support this loop. If a feature does not support this loop, question whether it should be frozen, deleted, or moved out of the main wedge.

51: ## Product Wedge Candidates
52:
53: When making product or architecture recommendations, evaluate these wedges.
54: **They are not peers — the ordering is the point.** The 2026-08 competitive
55: sweep ([`docs/market-research-2026-08.md`](docs/market-research-2026-08.md), and
56: §9 for the 2026-08-25 re-test) established that signed, offline-verifiable
57: receipts are **table stakes**, not a wedge: they ship in Microsoft's
58: `agent-governance-toolkit`, Pipelock, and protect-mcp/ScopeBlind. Lead with the
59: debit, cite the signature as supporting evidence, never as the differentiator.
60: See [`WEDGE.md`](WEDGE.md) §"Signed receipts are table stakes now".
61:
62: 1. **exactly-once economic authorization at the gateway boundary** — one
63:    accepted idempotency key yields at most one gateway dispatch **to the
64:    configured upstream MCP tool** and at most one ledger debit, linked by a
65:    single persisted chain, with a receipt on every path that finalizes or
66:    reconciles. (Local governed tools have no dispatch state machine.) This is the wedge. ("Exactly-once" is the
67:    deduplication term of art: never a duplicate charge, not always a charge.)
68: 2. **crash-semantics accounting** — **for the configured upstream MCP tool**, a
69:    genuinely ambiguous post-dispatch outcome becomes a distinct receipted state
70:    rather than a silent redispatch. Local governed tools fail closed into manual
71:    review; they have no dispatch state machine.
72: 3. agent authorization gateway
73: 4. usage metering layer for agent tools
74: 5. MCP governance proxy
75: 6. secure delegated tool execution API
76: 7. **signed receipt ledger for agent actions — demoted 2026-08.** Real here and
77:    worth saying, but no longer differentiating. Do not build or pitch around it
78:    as the wedge.
79: 8. **agent audit log platform — demoted 2026-08**, same reason.
80:
81: Do not recommend "full agent middleware platform" unless the narrower wedges are already credible.

90: ## 4. What this proves — and what it does not
91:
92: Proven against this code: exactly-once gateway authorization, debit, and
93: receipt finalization under replay, concurrency, conflict, and denial; and
94: that receipts are tamper-evident under the published key.
95:
96: Not proven by this harness, and not claimed:
97:
98: - **Production behavior.** Same code, different infrastructure (Postgres,
99:   Redis, a real upstream MCP server). A local pass is strong evidence about
100:   the logic, not a measurement of the production deployment.
101: - **Remote exactly-once.** The gateway guarantees one authorization, one
102:   debit, one finalized receipt. A remote side effect is exactly-once only if
103:   the upstream honors the forwarded idempotency key — the OpenAPI contract
104:   narrows the claim to exactly that, correctly.
105: - **The local tool is simulated.** `partner.notes.write` appends to a local
106:   JSONL file and is labeled `simulation: true` in discovery. Production's
107:   `partner.echo` is a real upstream call. The governance path is identical;
108:   the work at the end of it is not.
109:
110: To reproduce the invariants against production, an operator must issue a
111: wallet-scoped key and funded permit out of band. No agent should manufacture
112: production credentials, and this surface cannot: production-like
113: environments refuse to boot with `ENABLE_DEV_KEY_SELF_PROVISION` set, and
114: the handler independently returns 403 there.
FILE docs/tool-interface-authority.md
1: # The Tool Interface Is the Product Surface
2:
3: Design goal: an agent discovers a normal MCP tool, calls it normally, and
4: governance happens automatically because that is the only executable path.
5: The agent should not have to understand "Agent Middleware" as a product
6: category, learn `/v1/permits`, or construct `mcpContext`.
7:
8: The permit remains the cryptographically verifiable authorization object —
9: it is just an **implementation primitive, not a UX primitive**. On the
10: standard `/mcp` surface the middleware materializes the appropriate permit
11: from wallet policy at call time.
12:
13: The design for generalizing this — one `authority_required` envelope for
14: every insufficient-authority outcome, an explicit resume contract in the
15: remediation payload, and remediation that carries a live approval handle —
16: lives in [`authority-required-flow.md`](authority-required-flow.md).
17:
18: ## The decision an invoke gets
19:
20: Every `tools/call` on the standard surface resolves to one of three
21: outcomes, decided server-side:
22:
23: ```text
24: ALLOW             policy satisfied -> auto-permit -> execute -> signed receipt
25: REQUIRE_APPROVAL  policy demands a human -> approval-gated auto-permit ->
26:                   retryable pending_human_approval -> approve -> same call,
27:                   same Idempotency-Key -> execute -> signed receipt
28: DENY              constraint violated -> machine-actionable denial
29:                   (reason code + details + remediation), receipted where a
30:                   permit exists
31: ```
32:
33: ### ALLOW
34:
35: Unchanged: the server mints a bounded, signed, single-tool, short-lived
36: permit from the caller's wallet and runs the full
37: permit → meter → exactly-once dispatch → signed receipt pipeline.
38:
39: ### REQUIRE_APPROVAL
40:
41: When any active policy bundle for the caller's wallet sets
42: `human_approval_required`, the auto-minted permit carries
43: `requires_human_approval=true`, so the existing invoke-time approval gate
44: (Sentinel-backed, fail-closed) pauses the call:
45:
46: ```json
47: {
48:   "code": -32005,
49:   "message": "human_approval_pending",
50:   "data": {
51:     "error": "authority_required",
52:     "status": "pending_human_approval",
53:     "approval_id": "appr-…",
54:     "expires_at": "…",
55:     "remediation": {
56:       "type": "await_human_decision",
57:       "detail": "Nothing was charged. Retry the identical tools/call with the same Idempotency-Key once the approval is decided; the same permit and approval are reused."
58:     }
59:   }
60: }
61: ```
62:
63: Nothing is charged, no receipt exists, and the idempotency key is released —
64: the retry that polls the decision resolves to the *same* permit and the
65: *same* approval instead of paging a human again. Because that retry loop
66: depends on the key, approval-gated calls **require** a client
67: `Idempotency-Key` (or `params._meta["io.agentmiddleware/idempotency_key"]`);
68: without one the call is refused with
69: `idempotency_key_required_for_human_approval` and a remediation block.
70:
71: A key the client *does* supply — here, on the legacy MCP transports, or on
72: the governed AWI HTTP routes — must be usable: the contract (at most 128
73: characters, no control characters, one key per request, never trimmed or
74: replaced by a generated one) and the `invalid_idempotency_key` refusal are
75: specified in [`failure-semantics.md`](failure-semantics.md) under "What
76: counts as a key".
77:
78: An approval-gated auto-permit lives for the whole approval window
79: (`SENTINEL_APPROVAL_TIMEOUT_SECONDS`) plus the standard TTL as execution
80: margin, so a decision made late in the window still executes instead of
81: stranding as `permit_expired`.
82:
83: The gate satisfies only the policy's `human_approval_required` constraint.
84: Every other constraint in the bundle — tool allowlists, category allowlists,
85: `max_cost_per_action`, `daily_spend_limit`, `require_real_effects` — is
