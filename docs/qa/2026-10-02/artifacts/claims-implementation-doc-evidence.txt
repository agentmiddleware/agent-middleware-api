1:# Wedge: Replay-safe MCP permits and exactly-once debits
2:
3:Agent Middleware API should not initially sell itself as a full platform for
4:autonomous economic actors. The credible wedge is narrower:
5:
6:> Exactly-once gateway authorization, debit, and receipt finalization for
7:> metered MCP calls.
8:
9:Or in one line:
10:
11:> Authorize one agent action. Charge it once. Prove what happened.
12:
13:Start with the [documentation guide](docs/README.md) for the supported
14:evaluation, integration, SDK, security, and pilot paths.
15:
16:**What "exactly-once" means here, precisely.** It is the distributed-systems
17:term of art for the *deduplication* guarantee — no duplicate dispatch, no
18:duplicate debit — not a promise that every accepted call results in a charge.
19:Two paths produce no net debit at all: a crash before dispatch reconciles to a
20:refund, and an out-of-scope or over-budget call is denied before money moves.
21:The enforceable claim is **never a duplicate charge, not always a charge.**
22:Every precise statement of the guarantee below says "at most one" for that
23:reason. See [`docs/failure-semantics.md`](docs/failure-semantics.md).
24:
25:The core job is to put one enforceable **economic** boundary between autonomous
26:agents and tools:
27:
28:```text
29:scoped signed permit -> governed MCP invoke -> wallet charge -> signed receipt
30:-> ledger -> audit chain -> replay no double charge -> out-of-scope denial
31:```
32:
33:The loop now has a front door. Two questions an agent has to answer *before*
34:it can act — "may I?" and "what will it cost?" — are answered in the same
35:signed, checkable way as the action itself:
36:
37:```text
38:permit request -> human approves -> minted permit
39:signed quote   -> price locked   -> charge honors it
40:```
41:
42:Both feed the same loop rather than sitting beside it: the human's decision
43:mints an ordinary signed permit, and the quote is honored by the ordinary
44:metered charge. Neither adds a second way to authorize or to spend.
45:
46:Category language (“MCP trust plane,” “governance gateway”) is occupied. The
47:differentiating primitive is exactly-once economic authorization at the
48:gateway boundary: one idempotency key returns the original receipt without a
49:second gateway dispatch or debit. A remote tool's own side effect is exactly
50:once only when that tool also honors the forwarded idempotency key.
51:
52:## Positioning vs nearby products
53:
54:Stay a **closed-loop credit and delegated-authority** system for internal AI
55:platform teams—not a general MCP gateway and not merchant settlement.
56:
57:| Nearby | Their center of gravity | Our difference |
58:|--------|-------------------------|----------------|
59:| MCP “trust” gateways (e.g. signed receipts + replay) | Policy / evidence | Wallet debit + economic idempotency |
60:| MCP monetization / pay-per-tool | Payments rails | Internal budgets; no settlement claim |
61:| Enterprise authz for MCP | Who may call | Meter + receipt + charge-once |
62:| Agent reliability libraries (in-process decorators) | Retry safety inside the caller | A boundary the agent cannot route around; evidence a third party can check |

140:## What it guarantees
141:
142:| Guarantee | What it means | Proof |
143:|---|---|---|
144:| **Charge-once under retry** | Same idempotency key → same receipt, no second dispatch, no second debit. A changed payload under that key conflicts. | `tests/test_adversarial_five_claims.py` |
145:| **Budget containment** | A permit's `max_credits` is reserved by one atomic guarded `UPDATE`; concurrent invocations cannot over-spend it, including on SQLite. | `tests/test_permits.py`, `postgres_permit_concurrency` CI job |
146:| **Interrupted-call accounting** | For the configured upstream tool, one persisted chain links the idempotency record, reservation, debit, dispatch attempt, receipt, and audit event. Ambiguity after the send claim is receipted `delivery_uncertain`, never silently redispatched. Local governed tools have no dispatch state machine and fail closed into manual review. | [docs/failure-semantics.md](docs/failure-semantics.md) |
147:| **Offline-verifiable receipts** | Ed25519-signed; verifiable with no credentials and no network access to the issuer, using the SDK verifier or any JOSE tooling. | `GET /v1/receipts/{id}/portable`, `/.well-known/jwks.json` |
148:| **Authority before money** | Out-of-scope, expired, revoked, or tampered permits are denied with a reason code *before* any charge. When a valid permit was present, that refusal is itself a signed receipt. Unpermitted and unknown-tool calls fail closed without one. | `tests/test_adversarial_five_claims.py` |

155:## What it does not do
156:
157:- **Not universal exactly-once.** Gateway replay safety makes the *remote* side
158:  effect exactly once only if the upstream tool also honors the forwarded
159:  idempotency key.
160:- **Not proof of downstream effect.** The dispatch claim is committed *before*
161:  the network send, so it records the authority to send — not that a send
162:  happened, and never that the tool acted.
163:- **Not settlement or compliance.** An internal credit ledger, not merchant
164:  settlement, dispute handling, or a certified compliance record.
165:- **Not an IAM replacement.** Wallet isolation is application-layer
166:  authorization and query scoping; PostgreSQL RLS and a public multi-tenant
167:  isolation guarantee are not implemented.
168:- **Not a transparency log.** Receipts verify offline, but nothing is anchored
169:  externally, and audit chains are tamper-evident rather than immutable against
170:  an administrator who controls both the database and its chain metadata.
171:- **One adapter, one upstream.** MCP is the only live governed adapter, and
172:  upstream execution is limited to one operator-configured Streamable HTTP
173:  server and one exact tool.
174:- **No delegation chains.** Permits are reusable budget envelopes; parent
175:  delegation containment is not implemented.
176:- **No public SLA**, no KMS integration, and no approval for PHI, PCI, or
177:  regulated production records.

156:**"Can't we just log tool calls?"** Logs are written by the same system that
157:made the call and can be rewritten by anyone with database access. Receipts are
158:signed and chained, so tampering is *evident*. (Evident, not impossible — a
159:database administrator who can alter both the data and its chain metadata is
160:inside the trust boundary, and we say so.)
161:
162:**"Does exactly-once really hold across the network?"** For one accepted
163:idempotency key at our boundary: one gateway dispatch, one debit, one receipt.
164:A *remote* tool's own side effect is exactly once only if that tool also honors
165:the forwarded key. Anything broader would overstate the distributed-systems
166:guarantee.
167:
168:**"Why not just use an open-source library?"** If your problem is reliability,
169:do. A decorator library gives you idempotency, timeouts, and budget caps for
170:free, with no infrastructure. Two things it cannot give you: it protects only
171:the call sites that import it, so an agent that constructs a call another way is
172:simply not covered; and an in-process result cache is not evidence anyone
173:outside your team can check. Buy a boundary when you need those two properties.
FILE docs/denial-details.md
150:`PermitWriteContendedError`, which rolls back the entire reservation
151:transaction and frees the idempotency record. Nothing is spent, no counter
152:moves, and no attempt row is created.
153:
154:The caller receives JSON-RPC error code **`-32005`** (from `POST /mcp/messages`)
155:or HTTP **409** (from `POST /mcp/tools/{id}/invoke`), with the message
156:`permit_write_contended`. **Retry with the same idempotency key** — the rollback
157:freed that record, leaving no persisted reservation or dispatch state, so the
158:same-key retry runs a fresh compare-and-swap without replaying a denial. A
159:new-key retry is a separate call: it can dispatch in addition to a retry of the
160:original key, bounded only by the per-tool call cap when the permit sets
161:`max_calls_per_tool` (otherwise by the permit's budget and expiry). The cap
162:bounds the number of calls; it does not deduplicate across keys. The cross-key
163:duplicate guard (`MCP_UPSTREAM_DUPLICATE_GUARD`, validated at startup to be `off`, `log`, or `enforce`) runs in log-only mode by default
164:and does not prevent new-key retries. On Postgres, the permit row lock serializes
165:concurrent reservations, making this contention path practically unreachable; it
166:remains reachable on SQLite under high concurrency.

168:## What details deliberately do not say
169:
170:**Binding mismatches carry no values.** A caller that presents a permit bound
171:to a different wallet or key has not proved it is the subject, so the denial
172:names the binding that failed (`{"bound_to": "subject_wallet_id"}`) and nothing
173:about which wallet or key the permit actually belongs to. Everything else in
174:the table describes the caller's *own* permit, which it can already read at
175:`GET /v1/permits/{permit_id}`.
176:
177:**Forbidden fields echo the name, never the value.** The value is the thing the
178:permit forbade carrying.
179:
180:Reading a denial still requires being authorized for the permit: a foreign
181:wallet key is refused at `POST /v1/permits/verify` (403) before any verdict is
182:computed. Details enrich a refusal you were already entitled to see; they do
183:not widen who can ask.

130:def decode_idempotency_key_header(line: str) -> str:
131:    """Return an ``Idempotency-Key`` header line as the text the client sent.
132:
133:    Header bytes reach the application decoded as latin-1, so a key a client
134:    sent as UTF-8 would otherwise arrive as mojibake: it would not equal the
135:    same key sent in the body, and UTF-8 continuation bytes in 0x80-0x9F
136:    would read as C1 control characters. The line is re-read as UTF-8 and
137:    nothing else, so every wire value has at most one reading and two
138:    different byte sequences can never alias to one key; bytes that are not
139:    valid UTF-8 are refused (``idempotency_key_not_utf8``) rather than kept
140:    as latin-1 text.
141:    """
142:    try:
143:        return line.encode("latin-1").decode("utf-8")
144:    except UnicodeError as exc:
145:        raise InvalidIdempotencyKeyError(
146:            "idempotency_key_not_utf8",
147:            f"invalid_idempotency_key: {IDEMPOTENCY_KEY_HEADER_SOURCE} must be "
148:            "valid UTF-8",
149:            source=IDEMPOTENCY_KEY_HEADER_SOURCE,
150:        ) from exc

153:def resolve_client_idempotency_key(
154:    sources: Sequence[tuple[str, object]],
155:) -> str | None:
156:    """Reduce every explicitly supplied key source to the one key to honor.
157:
158:    ``sources`` holds ``(source_name, value)`` for each source the caller
159:    actually sent; absent sources are simply not listed. Every present value
160:    must validate, and when more than one source is present they must agree
161:    exactly. Disagreement is refused as ambiguous rather than letting one
162:    source silently win. Returns ``None`` only when no source was supplied.
163:    """
164:    validated: list[tuple[str, str]] = []
165:    for source, value in sources:
166:        validated.append(
167:            (source, validate_client_idempotency_key(value, source=source))
168:        )
169:    if not validated:
170:        return None
171:    first_source, first_key = validated[0]
172:    for source, key in validated[1:]:
173:        if key != first_key:
174:            raise InvalidIdempotencyKeyError(
175:                "idempotency_key_conflict",
176:                f"invalid_idempotency_key: {first_source} and {source} disagree; "
177:                "send one key, or the same key in both",
178:                source=f"{first_source}, {source}",
179:            )
180:    return first_key
