1:"""Permit requests: an agent asks, a human approves, the middleware mints.
2:
3:The invoke-time gate (``app.services.human_approval``) pauses a call under a
4:permit that already exists. This module covers the step before that: an agent
5:that has *no* authority asks a human for some, and gets a signed permit only
6:if a human says yes.
7:
8:    request -> notify -> approve -> mint -> poll
9:
10:    POST /v1/permit-requests   agent states scope, budget, and why
11:                               -> Sentinel pages the human, 202 pending
12:    GET  /v1/permit-requests/{id}
13:                               -> agent polls; on approval the permit is
14:                                  minted from the STORED terms and returned
15:
16:Three properties carry the security of the flow:
17:
18:**The human's decision binds to the reviewed terms.** Scopes, tools, budget,
19:and permit expiry are frozen on the row at request time and hashed into
20:``request_hash``. Minting reads that row — never the polling request — so
21:there is no window in which an approved request can be re-aimed.
22:
23:**Minting happens exactly once.** The ``pending -> minting`` transition is a
24:conditional UPDATE, so one caller wins even with concurrent pollers or two
25:workers. The permit id is reserved when the human is paged and used as the
26:minted permit's primary key, which makes a mint retried after a crash collide
27:on that key rather than issue a second permit carrying the same authority.
28:
29:**Expiry is enforced here.** Sentinel has no expired state (a timed-out
30:approval stays "pending" there forever), so ``expires_at`` is checked locally
31:before every poll and a decision arriving after the window is not honored.
32:
33:Fail-closed posture matches the invoke gate: simulated approvals are refused
34:in production-like environments, real mode without Sentinel configuration
35:refuses at request time, and a Sentinel outage is retryable rather than
36:silently minting.
